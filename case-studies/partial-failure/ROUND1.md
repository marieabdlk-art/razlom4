# Partial failure pilot — round 1

Четыре роли получили только публичный контракт из
`PARTIAL_FAILURE_PILOT_PLAN.md`. Ответы были независимы; инструменты и файлы
использовать запрещалось.

## Frozen proposals

### P1 — Архитектор: quarantined forward

Зафиксировать новый epoch, изолировать четыре v1/unknown узла и восстановить
обслуживание на шести v2. Новые заказы сначала помещаются во внешний
order-level ledger; временный adapter читает v1/v2 и пишет v2. Старые узлы
возвращаются только после reconcile.

Критическая assumption: каждый подтверждённый заказ существует хотя бы на
одном доступном узле либо во внешнем журнале. Kill-test: единственный заказ на
unknown-узле плюс потерянный ACK.

### P2 — Скептик: impossibility BLOCK

Rollback и forward недоказуемы: два недоступных узла допускают два мира с
одинаковыми наблюдениями и противоположным правильным действием. Допустимы
только новый recovery epoch, изоляция и `BLOCKED_UNKNOWN`.

Kill-test: unknown-узел принял и применил уникальный заказ, не отражённый ни в
status, ни во внешнем журнале. Retry дублирует эффект, restore теряет заказ.

### P3 — Упрощатель: minimal forward

Epoch fence, append-only log, один v1/v2 reader с v2-only writer и
детерминированная migration по `order_id + operation_id`. Неизвестные узлы не
влияют на active set.

Критическая assumption: каждый принятый заказ обнаружим. Если полнота не
доказана, исполнение прекращается и предложение схлопывается в BLOCK.

### P4 — Аварийщик: global BLOCK

Не мутировать данные до возврата unknown; зафиксировать только fence и recovery
evidence. Требования C1/C2 и C6 признаны одновременно невыполнимыми.

Kill-test: неразличимая пара «unknown применил migration и уникальную запись» /
«unknown ничего не применил».

## Конфликт

Раунд разделился 2:2. Forward-карточки предполагали полноту identity/history,
которой нет в контракте. BLOCK-карточки сохраняли safety, но глобально нарушали
двухминутную доступность. Среднего решения между этими позициями нет.
